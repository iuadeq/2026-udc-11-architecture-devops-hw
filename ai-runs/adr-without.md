# ADR-0001: Механізм сповіщень і точного повернення посилок

## Статус

Запропоновано

## Контекст (Context)

Сервіс «Поштомат громади» обслуговує мережу поштоматів. Поточна архітектура складається з:

- **API** (`src/server.js`) — HTTP-сервер на Node.js, який приймає реєстрацію посилок (`POST /parcels`), видачу за кодом (`POST /pickup`), адмінський список (`GET /admin/parcels`) та healthcheck (`GET /health`).
- **Worker** (`src/worker.js`) — фоновий процес, що кожні 10 секунд (`POLL_INTERVAL_MS`) опитує базу даних на предмет нових посилок без сповіщення і відправляє SMS з кодом отримання пачками по 50 (`BATCH_SIZE`). SMS надсилається через зовнішній HTTP API SMS-провайдера (`src/sms.js`), з вбудованим rate-limiting і retry з exponential backoff при отриманні 429.
- **Нічна задача** (`bin/expire-parcels.js`) — cron-скрипт, який знаходить посилки зі статусом `waiting`, що прибули понад 72 години тому (`RETURN_AFTER_MS`), позначає їх як `returned` і повідомляє кур'єрську службу через API (`src/courier.js`).
- **База даних** — PostgreSQL у продакшні (в пам'яті для тестів), пул з'єднань з обмеженням `max` і тайм-аутом `waitMs` (`src/db.js`).
- **Конфігурація** — усі налаштування зі змінних оточення (`src/config.js`): `DATABASE_URL`, `DB_POOL_MAX`, `SMS_BASE_URL`, `SMS_TOKEN`, `SMS_RATE_PER_SEC`, `COURIER_BASE_URL` тощо.

Нам потрібно:
1. Зберегти поточний механізм SMS про прибуття без змін.
2. Додати нагадування через 24 та 48 годин після прибуття (якщо посилку ще не забрали).
3. Повернення посилки відправнику рівно через 72 години від моменту прибуття, а не «наступної ночі» після закінчення 72 годин.

**Припущення** (у коді прямих відповідей немає):
- Навантаження невідоме; припускаю помірне — десятки-сотні посилок на день.
- Немає обмежень на додавання нових залежностей або сервісів.
- SMS-провайдер підтримує необхідний обсяг повідомлень без додаткових обмежень, крім rate-limiting, що вже обробляється в `src/sms.js`.
- Розгортання — docker compose, масштабування горизонтальне можливе.
- Немає специфічних правових обмежень щодо часу відправки SMS.

## Розглянуті варіанти

### Варіант A: Окремий scheduling-сервіс (Redis + BullMQ)

**Як працює:**
Додаємо Redis як message broker та бібліотеку BullMQ (або аналог) для відкладених задач. При реєстрації посилки (`POST /parcels`) API ставить у чергу три delayed jobs:
- нагадування через 24 години,
- нагадування через 48 годин,
- повернення через 72 години.

Окремий worker-процес (або розширений існуючий) обробляє задачі з черги. Якщо посилку забрали — відповідні jobs видаляються з черги.

| Аспект | Оцінка |
|---|---|
| **Плюси** | Точний час спрацювання (delayed jobs у BullMQ гарантують виконання ±секунди). Масштабується горизонтально. Не навантажує базу даних polling-запитами. Retry та dead letter queue з коробки. Чітке розділення відповідальності. |
| **Мінуси** | Нова залежність (Redis), яку треба розгортати, моніторити і бекапити. Додаткова складність інфраструктури. BullMQ — це npm-залежність, а проєкт зараз працює без жодних npm-пакетів. Потрібна обробка ситуації, коли Redis недоступний. |

### Варіант B: Розширення існуючого worker з таблицею scheduled_notifications у PostgreSQL

**Як працює:**
Додаємо в PostgreSQL таблицю `scheduled_notifications` з полями: `parcel_id`, `type` (reminder_24h, reminder_48h, return_72h), `scheduled_at`, `processed_at`. При реєстрації посилки API створює три записи з розрахованими часами спрацювання. Існуючий worker отримує додатковий polling-цикл: кожні 30–60 секунд перевіряє, чи є записи з `scheduled_at <= NOW()` і `processed_at IS NULL`, і обробляє їх. Якщо посилку забрали — записи або видаляються, або помічаються як скасовані.

| Аспект | Оцінка |
|---|---|
| **Плюси** | Жодних нових зовнішніх залежностей — усе в існуючому PostgreSQL. Простота розгортання і бекапів (дані в одному місці). Знайомий стек для команди. Транзакційна узгодженість: створення посилки і розкладу сповіщень — в одній транзакції. |
| **Мінуси** | Polling бази кожні 30–60 секунд — додаткове навантаження на PostgreSQL (хоча з індексом на `scheduled_at` це один легкий запит). Точність ±1 хвилина (залежить від інтервалу polling). При горизонтальному масштабуванні потрібна координація між worker-ами (advisory locks або `SELECT ... FOR UPDATE SKIP LOCKED`). |

## Рішення (Decision)

Обираємо **Варіант A — Redis + BullMQ**.

Головний аргумент: точність спрацювання. Нагадування і повернення мають відбуватися через конкретний час. Polling PostgreSQL дає точність ±1 хвилину, що може бути прийнятно для нагадувань, але для повернення через рівно 72 години (вимога замінити поточну нічну задачу) бажана вища точність. BullMQ гарантує виконання delayed job з точністю до секунди.

Додатковий аргумент: розділення відповідальності. Черга повідомлень — стандартний інфраструктурний патерн для відкладених задач. Redis легкий, добре задокументований, має persistence (AOF/RDB).

Idempotency: кожну задачу позначаємо унікальним `jobId` (`parcel:<id>:reminder_24h`), що запобігає дублікатам. Перед відправкою SMS worker перевіряє, чи посилка ще має статус `waiting`.

## Наслідки (Consequences)

**Що стає краще:**
- Точне спрацювання нагадувань і повернень (±секунди замість «наступної ночі»).
- Worker більше не потребує polling для нових типів сповіщень.
- Легко додавати нові типи відкладених задач у майбутньому.
- Нічна задача `bin/expire-parcels.js` стає непотрібною — повернення обробляє delayed job.

**Ціна і ризики:**
- Redis — нова залежність, яку треба розгортати поруч з PostgreSQL.
- BullMQ — перша npm-залежність у проєкті, ламає принцип zero-dependency.
- Якщо Redis впаде, нові нагадування не стануть у чергу (потрібен fallback або моніторинг).
- Потрібен окремий бекап Redis (або використання AOF persistence).

**Що треба зробити:**
- Додати Redis до docker compose.
- Додати BullMQ як npm-залежність в `app/`.
- Створити producer у `src/parcels.js` (при `registerParcel`) і consumer у `src/worker.js`.
- Додати cancel logic при `pickup` — видалення відкладених задач для цієї посилки.
- Додати нові змінні оточення: `REDIS_URL`, можливо `REDIS_PASSWORD`.
- Оновити `src/config.js`.
- Оновити моніторинг: алерт на недоступність Redis.
- Мігрувати нічну задачу: видалити cron, повернення обробляється delayed job у worker.

**Коли переглянути рішення:**
- Якщо Redis виявиться надлишковим для масштабу системи (десятки посилок на день).
- Якщо з'являться вимоги до транзакційної узгодженості, яких Redis не забезпечує.
- Якщо команда вирішить повернутися до принципу zero-dependency.
